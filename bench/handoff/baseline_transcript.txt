> Task: users report intermittent data loss during partition migration under load (bug #43). Investigate.

Let me pull the bug report.
$ cat reports/bug-43.md
  Title: Intermittent data loss during partition migration under load
  Severity: high
  Repro: only under sustained write load. During a partition migration, a small number of
  the most recent writes to the migrating partition are lost. Timing-dependent; ~1 in 40
  migrations under load, never observed at low load.

Let me look at the migration path.
$ sed -n '1,80p' src/shard/NodeTransfer.java
  public final class NodeTransfer {
    private final PartitionMap map;
    private final LeaseManager leases;
    // Called by PartitionManager to move a partition to this shard.
    void migrate(PartitionId pid, ShardId from) {
      Owner owner = map.ownerOf(pid);          // resolves current owner
      copyNodeState(pid, from);                // <-- copies BEFORE confirming ownership here
      map.setOwner(pid, self);
    }
    private void copyNodeState(PartitionId pid, ShardId from) { /* streams node state */ }
  }

So NodeTransfer copies node state and THEN sets ownership. During the copy, the source
shard is still the owner and still accepting writes. Any write that lands after the copy
window starts but before ownership flips is lost. That matches the repro.

First idea: distributed locking. Acquire a cluster-wide lock on the partition for the whole
migration so nobody writes during the copy.
$ sed -n '1,40p' src/shard/PartitionMap.java
  public final class PartitionMap {
    Owner ownerOf(PartitionId pid) { ... }     // maps partition -> owning shard
    void setOwner(PartitionId pid, ShardId s) { ... }
  }
I sketched a DistributedLock around migrate(). Let me benchmark lock vs no-lock under load.
$ ./bench/run.sh lock_vs_lease
  {
    "distributed_lock": { "p50_ms": 180, "p99_ms": 4200, "stalled_migrations": 37 },
    "lease":            { "p50_ms": 22,  "p99_ms": 140,  "stalled_migrations": 0 }
  }
Distributed locking is a non-starter: under load the lock causes heavy contention, p99
blows up to 4.2s and 37 migrations stalled. Rejecting distributed locking.

Second approach: time-bounded leases. LeaseManager already has what I need.
$ grep -n "public" src/shard/LeaseManager.java
  12: public boolean isOwner(PartitionId pid)
  18: public void    renew(PartitionId pid, Duration ttl)
Model: a partition is owned via a time-bounded lease; writes are only valid while the lease
is held and unexpired. No global lock, so no contention.

Root cause + fix: in NodeTransfer.migrate(), we must renew the lease on the destination
BEFORE calling copyNodeState(). If we hold a fresh lease before copying, the stale owner's
lease can be made to lapse and it stops accepting writes, so nothing is lost during the
copy. Current order (copy-then-own) is the bug.

PartitionManager coordinates partition assignment and migration across shards, fwiw.
